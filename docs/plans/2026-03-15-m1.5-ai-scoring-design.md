# M1.5: AI Scoring Layer Design

**Date:** 2026-03-15
**Status:** Approved
**Milestone:** M1.5 — AI Evaluation Layer

---

## Overview

Add an AI evaluation layer between plugin fetch and database upsert. Every new listing that passes keyword scoring is evaluated by a local LLM (free, via Ollama). An optional second pass using Anthropic Sonnet confirms escalation decisions before high-priority alerts fire.

The feature is fully opt-in: `ai.enabled = false` in config makes the evaluator a no-op passthrough with zero behavior change from M1.

---

## Architecture

### Integration Point

The daemon poll loop gains one step:

```
plugin.fetch()
    → score_listing()          # keyword scoring — M1
    → ai_evaluate()            # NEW: AI filter + explain + escalate
    → upsert_listing()
```

`ai_evaluate()` only runs on listings with `relevance_score > 0`. Keyword failures are still discarded before hitting the AI.

### New Files

```
src/scavenger/
├── ai/
│   ├── __init__.py
│   ├── evaluator.py      # AIEvaluator class — calls LiteLLM
│   ├── models.py         # AIEvaluation Pydantic model
│   └── prompts.py        # prompt templates
```

### LiteLLM Gateway

Self-hosted LiteLLM instance (Docker, Proxmox or local machine) as the unified gateway. Routes to:
- **Ollama** (local, free) — filter pass, runs on every listing
- **Anthropic Haiku/Sonnet** (optional, opt-in) — escalation confirmation only

SCAVENGER talks to LiteLLM via the OpenAI-compatible `/chat/completions` endpoint. Model switching requires only a config change, no code change.

## Configuration

`~/.config/scavenger/ai.toml`:

```toml
[ai]
enabled = true
litellm_base_url = "http://localhost:4000"
filter_model = "ollama/qwen2.5:7b"
escalation_model = "anthropic/claude-haiku-4-5"
escalation_enabled = false        # opt-in, off by default
escalation_min_keyword_score = 70 # only escalate-check high keyword scores
```

Recommended local model: `qwen2.5:7b` or `llama3.2:3b` (solid at structured classification).

## Data Model

### AIEvaluation (`ai/models.py`)

```python
class AIEvaluation(BaseModel):
    relevant: bool       # False = discard before upsert
    reason: str          # 1-2 sentences, shown in TUI detail panel
    notable: str | None  # "SSM variant, typically $200 above asking"
    escalate: bool       # overrides alert_priority to high
```

### Schema Change

```sql
ALTER TABLE listings ADD COLUMN ai_evaluation TEXT;  -- nullable JSON
```

Applied at daemon startup via `db.migrate()`. M1 listings without `ai_evaluation` render normally — graceful degradation.

## AIEvaluator (`ai/evaluator.py`)

```python
class AIEvaluator:
    def __init__(self, config: AIConfig): ...

    async def evaluate(self, profile: Profile, listing: Listing) -> AIEvaluation:
        """Evaluate a listing against a profile. Returns passthrough on error."""
        ...

    async def is_enabled(self) -> bool: ...
```

**Call flow:**

1. Build prompt from `prompts.py` — system prompt includes JSON schema, profile name, keywords, negative keywords
2. POST to LiteLLM `filter_model` via httpx (reuses existing dep)
3. Parse response JSON into `AIEvaluation`
4. On parse failure → return `AIEvaluation(relevant=True, reason="", notable=None, escalate=False)` — never drop a listing due to model error
5. If `relevant=False` → listing discarded, never hits DB
6. If `escalate=True` AND `escalation_enabled` AND `keyword_score >= escalation_min_keyword_score` → second call to `escalation_model` to confirm

**Error handling:** Any httpx or JSON error returns the passthrough evaluation. A flaky or slow local model never blocks the poll loop — timeout set to 10s for filter pass, 15s for escalation.

## Prompt Design (`ai/prompts.py`)

**System prompt:**
```
You are an expert in {profile.name}. A user is searching for items matching their interest profile.
Evaluate the listing below and respond ONLY with valid JSON matching this schema:
{{"relevant": bool, "reason": "string", "notable": "string or null", "escalate": bool}}

Profile keywords: {keywords}
Negative keywords (any match = not relevant): {negative_keywords}
Price range: {price_range}

Rules:
- relevant: false if any negative keyword appears or item clearly doesn't match
- reason: 1-2 sentences explaining your decision, shown to the user
- notable: only if there is something specific worth highlighting (rare variant, underpriced, misidentified by seller). null otherwise.
- escalate: true only if this is an unusually good opportunity the user should see immediately
```

**User prompt:**
```
Title: {listing.title}
Price: {listing.price}
Description: {listing.description}
```

## Integration into Daemon (`daemon/main.py`)

```python
class Daemon:
    def __init__(self, config: AppConfig, ai_config: AIConfig | None = None):
        ...
        self._evaluator = AIEvaluator(ai_config) if ai_config else NoopEvaluator()

    async def _poll_profile(self, profile: Profile) -> list[Listing]:
        ...
        for listing in fetched:
            listing.relevance_score = score_listing(...)
            if listing.relevance_score == 0.0:
                continue
            # NEW
            evaluation = await self._evaluator.evaluate(profile, listing)
            if not evaluation.relevant:
                continue
            listing.ai_evaluation = evaluation.model_dump_json()
            if evaluation.escalate:
                listing.alert_priority_override = "high"
            if await self._db.upsert_listing(listing):
                new_listings.append(listing)
```

`NoopEvaluator` returns the passthrough evaluation and satisfies the same interface — no conditionals needed in `_poll_profile`.

## TUI Surface (consumed by M2)

Data is stored, M2 renders it:

- **Result card**: `notable` shown as a highlighted badge if present — `★ SSM variant, typically $200 above asking`
- **Detail panel**: `reason` in a dedicated "AI Notes" section below description
- **Escalated listings**: distinct color/icon treatment
- **No AI evaluation**: M1 listings render normally — graceful degradation

The TUI never calls AI directly. All evaluation is daemon-side.

## Testing Strategy

### Unit tests (`tests/test_ai_evaluator.py`)

Mock httpx — no live LiteLLM calls:

- Valid response → `AIEvaluation` parsed correctly
- Malformed JSON → passthrough returned, listing not dropped
- `relevant=False` → listing discarded before upsert
- `escalate=True` + conditions met → second escalation call fires
- `escalate=True` + `escalation_enabled=False` → no second call
- httpx timeout → passthrough returned

### Prompt tests (`tests/test_ai_prompts.py`)

Pure string assertions — no network:

- Rendered prompt contains profile name, keywords, negative keywords
- JSON schema present in system prompt
- Negative keywords correctly formatted

### Fixtures

`tests/fixtures/ai_evaluation_sony.json` — canned `AIEvaluation` response for Sony A-mount profile, used across multiple tests.
